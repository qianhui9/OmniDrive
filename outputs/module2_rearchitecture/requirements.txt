# Codex 任务：OmniDrive M2 第三轮优化——突破计算复用粒度与收益上限，实现真正有净收益的状态化视觉执行

## 一、项目背景与任务目标

你是一名熟悉 PyTorch、CUDA、Transformer 计算依赖、自动驾驶视觉感知、GPU Runtime 和 VLM 推理优化的研究型系统工程师。

本轮不是继续简单提高 Window Packing 的 Kernel 性能，而是重点解决当前研究设计与 OmniDrive 实际模型计算结构之间的矛盾。

### 当前核心问题

此前实验表明：

1. M1 能够建立部分世界状态关联，但真实有效区域难以形成完整 EVA Attention Window。
2. Exact M2 当前主要复用 EVA 最前面的两个 Window Attention Blocks。
3. Global Attention 导致局部变化向整个相机 Token 范围传播，后续仍需大量完整计算。
4. M1 的真实在线验证成本约 189–215 ms。
5. 当前受控完整 EVA 的最优计算节省约 50 ms，不足以覆盖完整 M1 开销。
6. 四个真实 nuScenes Scene 中，实际可复用完整 Attention Window 为 0。
7. 非零局部跳算虽然实现了真实 GPU 计算跳过，但尚未通过冻结的 Detection/Map 质量约束。
8. 当前 Optimized M1+M2 端到端加速比为 0.959×，仍然慢于原始 OmniDrive。

因此，本轮研究必须回答：

**如何突破现有 Window-Level Incremental Execution 的复用粒度与计算收益限制，使历史世界状态能够在任务质量约束下转化为真正有净收益的视觉计算复用？**

### 核心优化目标

优先最小化真实视觉推理服务时间：

[
\min T\_{\mathrm{visual\ service}}
]

需要计入：

[
T\_{\mathrm{total}}=
T\_{\mathrm{validation}}+
T\_{\mathrm{cache}}+
T\_{\mathrm{planning}}+
T\_{\mathrm{GPU}}+
T\_{\mathrm{sync}}
]

同时保持：

- 正确的模型计算依赖；
- 不超过预先冻结的数值或任务质量约束；
- 正确的状态时间戳、版本和时序记忆；
- 对新目标、动态目标和不可见区域的必要刷新；
- 无收益情况下的低成本完整执行回退。

不要通过人为缩小刷新区域、降低 Oracle 标准或直接继承未经验证的深层特征来制造加速。

# 二、总体执行策略：先验证收益上限，再决定具体改进路径

本轮必须分阶段推进，而不是直接设计一个新的复杂缓存算法。

**阶段 A：理论收益上限与计算瓶颈诊断。**

**阶段 B：非零稀疏执行的数值误差归因与修复。**

**阶段 C：低成本复用机会筛查与按需状态维护。**

**阶段 D：扩大合法计算复用边界。**

其中，阶段 A 是所有后续代码设计的依据。

如果实验证明某个优化方向无法覆盖自身成本，应及时停止该方向，保留诊断结果，不要继续堆叠算法。

# 三、阶段 A：分析当前 EVA 增量计算的真实收益上限

## A1. 分解 OmniDrive 完整视觉计算成本

基于当前实际模型与 RTX 3090 环境，测量：

- Patch Embedding；
- EVA Block 0；
- EVA Block 1；
- EVA Block 2（Global Attention）；
- EVA 其余 Window Blocks；
- EVA 其余 Global Blocks；
- Backbone 输出整理；
- Detection Head；
- Map Head；
- Carrier Query 生成；
- LLM Prefill/Decode（只测量，不修改）。

测量 P50/P95、CUDA GPU Time、CPU Wall Time、显存与 Kernel 数量。

不要使用理论 FLOPs 代替真实性能。

## A2. 建立不同复用范围对应的计算收益上限

至少分析以下情况：

- 仅复用 Block 0/1 中的部分 Window；
- 完整跳过 Block 0/1；
- 完整跳过指定早期 EVA Blocks；
- 复用某一个 Camera 的完整 Backbone 输出；
- 复用多个 Camera 的完整 Backbone 输出；
- 当前所有 Camera 的 EVA 输入完全重复。

上述实验中，只有实际满足依赖与输入一致性的情况才能进入正式执行。

对于不具备现实有效性条件的情况，可以使用受控 Oracle 实验测量理论收益上限，但必须标记为 Idealized Upper Bound，不得当成真实系统加速。

特别分析：

**如果 M2 最多只能节省前两个 Window Blocks 的约 50 ms，而 M1 需要约 200 ms，那么在当前同步流水线下，是否存在任何可能实现正向端到端加速的路径？**

请使用实测成本回答，而不是仅做定性推断。

## A3. 建立 Break-Even Feasibility Analysis

对于每一种候选计算复用范围，计算：

T\_{\mathrm{full}}-T\_{\mathrm{reuse}}
]

并与：

T\_{\mathrm{M1}}+T\_{\mathrm{M2,overhead}}
]

比较。

输出：

- Computation Saving Upper Bound；
- Validation Overhead；
- Cache Maintenance Cost；
- GPU Execution Overhead；
- Required Reuse Coverage；
- Break-Even Threshold；
- 实际可实现的复用覆盖率。

明确区分实测收益、受控上限和模型推断。

生成：

`outputs/module2_rearchitecture/feasibility_report.md`

**阶段 A 的目的，是决定之后应继续优化 Window-Level Sparse，还是需要扩展视觉复用的执行边界。**

# 四、阶段 B：定位并修复非零局部跳算的数值误差

当前非零 Window 更新在受控实验中未通过冻结的下游质量约束。

不能直接认定其误差全部属于浮点正常波动，也不能直接认为 Dependency Closure 一定错误。

需要进行层级误差归因。

## B1. 比较三种计算路径

使用相同输入、模型权重、随机种子和执行条件，比较：

**Path A：Original Full EVA**

使用原始 OmniDrive 完整 Forward。

**Path B：Dense Execution with Packed Layout**

使用与 M2 相同的 Window Packing、Attention/MLP 调用和输出重建过程，但更新全部 Window，不复用历史计算。

**Path C：Exact Sparse Execution**

只执行依赖闭包中的变化 Window，对已证明不受影响的 Window 读取历史缓存。

比较：

- Block 0；
- Block 1；
- Global Block 2；
- 后续 Backbone Feature；
- Detection；
- Map；
- Temporal Memory；
- LLM 输出。

目的在于区分：

- 原始 Block 与 Packed Block 的数值差异；
- 因 Batch Shape 变化产生的浮点执行差异；
- 真正由缓存复用引入的额外误差；
- 误差通过后续 Global Attention 的传播；
- Top-K 排序与 Temporal Memory 对微小数值变化的敏感性。

## B2. 重点检查具体代码

- `worldstream/m2/window_executor.py`
- `worldstream/m2/packing.py`
- `worldstream/m2/dependency_planner.py`
- `worldstream/m2/runtime.py`
- EVA `Block._forward()`
- EVA Attention、RoPE、Norm、MLP 和 Padding。

重点核查：

- Padding Token 是否按照原始 EVA 语义计算；
- FlashAttention 使用的实际 Batch Layout；
- FP16 Q/K/V 与 FP32 激活的舍入差异；
- Packed 和 Full 执行的 Attention Scale；
- LayerNorm 和 MLP 的输入差异；
- Output Stride 和内存布局；
- Residual 路径；
- 历史缓存的真实版本及输入依赖。

## B3. 正确性修复原则

优先修复确定的执行语义错误。

对于仅由不同 Kernel 实现引起的数值差异，需要先测量完整 Dense-to-Dense Variation，再判断 Sparse 额外误差。

不能直接放宽此前冻结的：

- Detection Center Difference ≤ 1 cm；
- Map Control Point Difference ≤ 1 cm；
- Greedy Text Exact；
- Planning Output Exact。

如果原始计算语义完全一致仍不能满足这些实验回归目标，应明确报告不可通过，并保留正式 Auto 的完整回退。

不要为通过测试而悄悄更改阈值。

输出：

`outputs/module2_rearchitecture/numerical_diagnosis.md`

# 五、阶段 C：实现低成本筛查与按需状态维护

当前 M1 验证成本较高，但对于严格计算复用，某些输入条件可以利用廉价必要条件提前判断不可能复用。

例如，当前图像和历史图像某些必要像素已经发生变化，就可以排除对应 Window 的精确复用。

但某几个采样点相同，不能证明整个 Window 可复用。

建议设计：

**Cheap Reuse Rejection Gate**

目标是用远低于完整 M1 的成本快速拒绝没有精确复用机会的请求。

## C1. 实现低成本必要条件检查

在当前完整 M1 验证之前，可先基于实际预处理后的当前/历史图像进行低成本检测。

优先利用现有：

- `exact_pixel_changes()`
- `cpu_window_opportunity()`
- 采样拒绝机制；
- Input Execution Signature。

要求：

1. 只允许快速拒绝，不允许仅凭采样通过就接受复用。
2. 对每个候选 Window，只要发现确定变化的必要输入，就排除精确复用。
3. 若所有 Window 均被证明不可能复用，可以直接选择完整 EVA 计算。
4. 若存在潜在复用机会，再执行必要的完整验证。
5. 计入图像访问、数据传输和 CPU/GPU 同步成本。

## C2. 解决 M1 状态维护语义

这是关键要求。

不能简单通过 Early Return 跳过 M1 `precheck()`，然后继续沿用历史 WorldStateManager。

如果减少 M1 验证频率，必须正确处理：

- 历史 Anchor 状态；
- Feature Version；
- Computation Timestamp；
- Verification Timestamp；
- Scene Continuity；
- M1 下一帧重新进入时的状态来源；
- StreamPETR Temporal Memory。

可以考虑安全策略：

当 Cheap Gate 证明精确计算复用无机会时，当前帧执行完整视觉模型，并根据真实完整感知结果对需要的 World State 进行重新初始化或合法更新。

但必须检查现有 M1 的 `commit()` 与初始化契约。

如果无法证明跳过 `precheck()` 后状态仍然正确，则暂时保留原 M1 完整执行，不启用该快速路径。

## C3. 实现 Cost-Aware Admission

只有当预计计算收益能够超过：

- 必要认证开销；
- 缓存开销；
- GPU 增量执行成本；
- 调度与同步开销；

才允许进入增量路径。

采用实测成本表和简单判据。

不要设计多级状态评分或强化学习调度器。

同时区分：

- 必须维持 M1 历史状态的服务；
- 只需要当前完整视觉输出的服务。

后一种情况可能具备更简单的完整计算回退条件；不能把两种任务的状态要求混淆。

# 六、阶段 D：研究并实现更合理的视觉计算复用边界

这是本轮最重要的方法设计任务。

**目标不是继续强行增加可复用 Attention Window 数量，而是根据 OmniDrive 的真实计算依赖，寻找具有更高收益上限且能够验证正确性的计算边界。**

请优先研究两个候选方向。

## D1. 优先实现：Exact Per-Camera Backbone Reuse

OmniDrive 的 EVA 主要对多个 Camera 图像进行视觉编码。

请首先确认当前实际 EVA Backbone 是否在相机之间独立执行，是否不存在跨 Camera 的 Attention 依赖。

如果满足这一条件，研究以 Camera 为复用单元的完整 Backbone 缓存。

例如，六个 Camera 中，某个 Camera 的完整预处理输入与历史缓存完全一致，并且：

- Camera ID 一致；
- Backbone 权重和执行环境一致；
- Position Embedding 一致；
- 预处理结果完全一致；
- 没有与历史状态不兼容的随机算子；
- 历史 Backbone 输出来源及版本有效。

则可以尝试直接复用该 Camera 的完整 EVA 输出。

对于发生变化的 Camera，正常执行 EVA。

最后按照原始 Camera 顺序拼接特征，再继续执行完整 Detection、Map、Temporal Memory 和 LLM。

**注意：Camera 级 EVA 复用不意味着可以复用 Detection/Map 的当前输出。**

当前 Ego Pose、历史 Memory、时间戳及下游感知必须按照实际输入继续执行。

必须验证：

- 不同 Camera Batch Shape 对数值结果的影响；
- 最终 Feature Stride；
- Camera 顺序；
- Position Embedding；
- 完整下游 Detection/Map/Memory；
- 显存成本；
- GPU 实际计算节省。

首先支持真正完全相同的预处理输入。

不能将经过光流变换后“看起来相似”的图像当成 Exact Cache Hit。

如果这种方式在受控重复请求中有收益，可作为一个独立的精确复用执行边界保留。

## D2. 条件研究：World-Aligned Approximate Feature Reuse

如果 D1 只能覆盖少量真实驾驶帧，请利用 M1 已有的 World Anchor 和 Dense Source Map，开展独立的近似计算复用可行性实验。

研究问题是：

在相机运动以后，能否利用经过验证的世界状态对应关系，对历史早期视觉表示进行合法的空间对齐，从而减少当前视觉计算？

候选内容：

- Patch Embedding 后的局部特征；
- 早期 EVA Window Feature；
- 某个 Camera 的部分视觉编码状态。

但必须认真处理：

1. 历史图像特征与当前坐标之间的空间对应。
2. Absolute Position Embedding。
3. RoPE。
4. 目标运动和遮挡。
5. 新出现区域。
6. 跨 Token Attention 依赖。
7. Global Attention 传播。
8. 错误复用对 Detection、Map、Memory 和 LLM 的影响。

不要直接将历史深层 Token Warp 到当前位置就声称得到当前正确特征。

建议先完成离线 Oracle 实验：

- Full Current Feature；
- Reused/Aligned Historical Feature；
- Feature Error；
- Detection/Map Error；
- Memory Drift；
- Greedy LLM Output；
- Planning Quality；
- Real Execution Cost。

如果无法获得可接受的质量与成本收益，就停止该方向，不必实现在线正式路径。

如果有充分正面证据，再实现具有独立开关的 Approximate Experimental Mode。

默认 Auto 不允许使用未经验证的近似缓存。

## D3. 不建议的实现方式

本轮不要：

- 修改 EVA 原始 Window Size；
- 重新训练完整 OmniDrive；
- 任意丢弃 Global Attention；
- 把物理 Anchor Valid 当作 Feature Exact；
- 强行复用整个 StreamPETR Query；
- 修改现有权重来掩盖误差；
- 将理论 FLOPs 减少称为实际 GPU 加速；
- 在没有质量验证的情况下扩大 Auto 的可执行更新集合。

# 七、阶段 E：完整实验设计

本轮实验必须围绕以下三个问题：

**是否扩大了合法复用范围？**

**是否降低了获得复用机会的额外成本？**

**是否最终改善完整 VLM 的实际执行时间？**

## E1. 受控正确性实验

包括：

- 完全重复输入；
- 单个 Camera 完全重复；
- 多个 Camera 完全重复；
- 单 Patch 变化；
- 一个 Window 变化；
- 多个 Window 变化；
- 自车姿态变化但视觉输入相同；
- 场景切换；
- 缓存版本变化；
- 连续多帧交替执行。

比较原始 Baseline、现有 M2 和新的计算复用方式。

重点测量：

- Backbone Error；
- Detection Center Difference；
- Map Control Point Difference；
- Temporal Memory Difference；
- Greedy Text；
- Planning Error；
- 实际跳过的 GPU Kernel；
- End-to-End Latency。

## E2. 真实 nuScenes 实验

继续使用现有四个 Scene，并尽可能增加新的独立 Scene。

至少包括：

- 转弯；
- 直行；
- 动态车辆；
- 行人；
- 遮挡；
- 不同帧间隔；
- 低光照场景。

不得将重复图像实验混入真实移动相机实验。

分别统计：

- Exact Window Reuse；
- Exact Camera Reuse；
- Approximate Reuse（如果经过验证）；
- Full Fallback；
- Validation Overhead；
- Cache Overhead；
- Actual GPU Work Saved；
- EVA Latency；
- Vision Pipeline Latency；
- Complete VLM Latency。

## E3. 计算收益上限分析

至少比较：

- 原始 OmniDrive；
- 原始 M1+M2；
- 低成本筛查版本；
- 改进后 Exact Window Execution；
- Exact Per-Camera Execution；
- 经质量验证的 Approximate Experimental（如适用）。

此外应报告独立的 Idealized Upper Bound，以证明各方案能节省多少计算，但不将其当作真实运行结果。

## E4. 按需维护消融

比较：

- 每帧完整 M1 验证；
- Cheap Gate + 必要完整验证；
- Cheap Gate + 经验证的安全重置/重新初始化；
- 不进行复用的 Full Baseline。

重点确认 Cheap Gate 节省的 CPU 时间是否大于其自身开销，且没有破坏连续场景状态。

## E5. 连续状态漂移实验

对存在非零复用的实验，增加较长连续序列，分析：

- Detection/Map 误差是否随时间累积；
- Temporal Memory 是否发生不同 Slot 保留；
- 关键目标是否被遗漏；
- 场景切换和回退是否能正确恢复状态；
- 多次近似复用是否导致漂移。

不允许仅用单帧的特征误差判断长期可靠性。

# 九、必须设置的阶段性决策条件

本轮需要明确的 Go/No-Go 决策，而不是无论结果如何都继续增加复杂算法。

### Gate A：Window-Level Reuse 是否值得继续？

若实测表明当前两层 Window 复用节省上限明显低于必要 M1 开销，且没有合法方式降低前置成本，则不要继续投入大量时间优化 Window Kernel。

保留现有 GPU Packing 作为已完成的底层优化组件。

### Gate B：非零局部跳算是否通过质量验证？

如果独立数值检查和下游任务实验仍不满足冻结约束，正式 Auto 必须继续回退。

不得为了允许更多更新数量而修改原有质量目标。

### Gate C：Per-Camera Reuse 是否具有实际计算收益？

若完全相同输入下的 Per-Camera Cache 通过数值质量验证且实际节省 GPU 工作，则保留。

若 Camera 独立性不成立或者 Cache Gather/Scatter 成本超过收益，则停止该方向。

### Gate D：世界对齐近似复用是否具有可行性？

必须同时满足可接受的特征误差、任务质量、状态连续性和实际成本收益。

否则只保留离线可行性分析，不进入在线正式执行。

### Gate E：完整 VLM 是否有净收益？

只有完整模型端到端时延低于 Baseline，同时质量约束成立，才可声明实际加速。

如果没有获得正向收益，应明确说明当前 EVA 和 M1 的结构性限制，并提出下一阶段需要改变的计算边界。
