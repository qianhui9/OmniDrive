# Codex 任务：OmniDrive M2 冻结收尾与 M3 任务条件化 VLM 服务优化

## 一、任务目标

项目目录：

`/data/qh/phdCode/work4/OmniDrive`

首先检查实际 HEAD、代码及历史实验结果，以实际实现为准，不覆盖用户已有修改。

1. 完成 M2 Conditional Prefix 的最后一次准入瓶颈归因，冻结已经验证的 M2 Exact Runtime。

## 2.2 完成来源复用准入漏斗

如果依旧没有足够的完整 Window 或质量—收益空间，确认当前 Conditional Prefix 路线 No-Go，停止继续研发此计算边界。

## 2.3 清晰区分 Exact 与 Research Conditional

当前研究配置使用 `mode='exact'` 强制执行实验性路径，容易造成语义混淆。

在不改变已有正式运行策略的前提下，完善诊断标识：

- `full`
- `exact`
- `experimental_conditional_forced`

分别记录：

- `exact_reused_windows`
- `conditional_reused_windows`
- `actual_skipped_block_computations`
- `reuse_source_frame/version`
- `quality_qualified`
- `performance_qualified`
- `fallback_reason`

实验性结果不得记录为正式 Exact 计算等价。

保留独立研究缓存，不能污染正式 M2 Cache。

如果实验性特征已经影响 Temporal Memory，则随后仅刷新 EVA 不得被标记为整个系统状态恢复。应重新初始化合法的下游状态，或使用可靠快照重新执行。

本阶段结束后，除必要的正确性修复外，不再修改 M2 的核心执行算法。

# 四、第三阶段：实现任务证据驱动的状态查询

本轮优先研究一种简单机制：

**Task-Evidence-Gated Serving**

核心思想：

在当前任务所需信息已经由合法、完整且足够新鲜的状态提供时，尝试避免再次进行完整 LLM Generation；否则继续原始 OmniDrive 推理。

不新增复杂世界模型，不引入加权置信度评分器。

## 4.1 复用已有 M3

优先扩展：

- `world_state.py`
- `post_perception.py`
- `task_conditioner.py`
- `runtime.py`
- `scheduler.py`

不要重写已有 Prefix KV Cache、Prefill Executor 或独立视觉状态维护器。

建议新增一个轻量 `TaskEvidenceContract` 或等价结构，包含：

- `task_type`
- `task_template`
- `referent_id`
- `scene_id`
- `frame_id`
- `timestamp`
- `source_frame/version`
- `current_observation_available`
- `task_required_fields`
- `available_fields`
- `referent_unique`
- `task_input_complete`
- `state_fresh`
- `contradiction_free`
- `quality_certificate`
- `answer_format`

这些字段只描述任务所需证据，不引入复杂的多级状态机。

## 4.2 严格任务准入

只针对输入需求能够明确列举的任务研究直接查询，例如：

- 唯一可指称对象的局部距离。
- 已确定对象的局部位置属性。
- 具有明确范围和完备检测证据的局部属性查询。

是否真正支持这些任务，以实际模型输出和离线独立质量评价为准。

禁止直接短路：

- 全局安全判断。
- 复杂驾驶决策。
- 规划轨迹生成。
- 未知对象的存在性判断。
- 缺少完整场景覆盖的计数任务。
- 无法唯一指称的对象问题。
- 来源过期或缺少当前证据的问题。

特别注意：

**历史 Object Identity 连续，不能证明该对象当前的位置、速度或周围关系仍然正确。**

当前 Head 与历史记录预测一致，也只代表预测一致性，不等于独立物理真值。

对于状态证据不完整的请求，必须保留 Unknown 并正常执行原始 VLM。

## 4.3 设计最小 Direct Query 执行路径

实现：

`Task Request → Evidence Check → Direct Query / Original VLM`

要求：

1. 请求必须符合明确的任务语法和输出格式。
2. 任务必须具有唯一的场景指称。
3. 来源签名、时间、版本及所需字段完整。
4. 缺少当前证据时不直接使用历史事实。
5. 不使用离线 GT 进行在线判断。
6. 状态查询与原始模型输出格式兼容。
7. 无法回答时完整回退，不生成猜测结果。
8. 保留每次准入、拒绝与实际省略的模型计算记录。

先实现：

`shadow_evaluation=True`

在 Shadow 模式中同时运行状态查询和原始 VLM，只作质量比较，不计入实际节省。

当具备独立质量证据后，再实现一个显式开启的实验性真正短路路径，确保被短路请求没有执行对应 LLM Prefill/Decode。

正式 Auto 默认关闭，不能因为 Shadow 结果很好就自动启用。

如果当前 OmniDrive 原生任务中没有符合证据条件的请求，就保留 Shadow 与拒绝统计，不人为构造大量简单问题宣称真实工作负载加速。

新增受控问题仅作为功能验证，必须与原始任务人口分开。

# 九、执行顺序与停止条件

按照以下顺序实际推进：

**Step 1：M2 最终诊断与冻结。**

完成准入漏斗和小范围语义清理；保留 Exact、默认关闭 Conditional，不再扩大视觉缓存算法。

**Step 2：M3 工作负载剖析。**

准确量化 Vision、Prefill、Decode、上下文构造、状态维护和任务人口，判断可获得的最大收益。

**Step 3：任务可回答性评价。**

复用已有 M3 World State/Post-Perception，建立严格证据契约，统计真正输入完备的问题。

**Step 4：实现 Shadow Task Query。**

不跳过原始 VLM，先验证状态查询质量及拒绝正确性。

**Step 5：实现实验性 Direct Query。**

仅对已获得充分任务质量证据的任务，真正跳过 LLM Generation；其余请求完整回退。

**Step 6：集成已有 Exact Prefix Fallback。**

保持输入、来源及缓存计算等价性，不新增近似 Prefix 策略。

**Step 7：真实 nuScenes 完整服务实验。**

比较原始模型、Persistent State 服务、M3 Shadow、Direct Query 与 Exact Prefix，报告任务质量和 E2E 收益。

最终分别输出：

| Gate | 判断内容                            |
| ---- | ------------------------------- |
| G1   | M1/M2 冻结接口及 Exact 正确性           |
| G2   | M2 当前计算边界的完整 No-Go 证据           |
| G3   | M3 真实任务与 Prefill/Decode 工作负载分析  |
| G4   | 状态输入对目标任务是否完备                   |
| G5   | Direct Query 正确性与独立质量证据         |
| G6   | Exact Prefix/Direct Query 执行正确性 |
| G7   | 同服务 E2E 净收益                     |
| G8   | 完整模型与工程回归                       |
